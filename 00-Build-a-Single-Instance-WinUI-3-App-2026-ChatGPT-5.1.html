1 Prerequisites & project setup

This guide assumes a packaged WinUI 3 desktop app built on the Windows App SDK 1.8 “Blank App, Packaged (WinUI 3 in Desktop)” template in Visual Studio (C#), as described in the official “Create your first WinUI 3 app” article and the DrumPad tutorial series. :contentReference[oaicite:1]{index=1}

High-level flow

  1. Create the template WinUI 3 packaged app.
  2. Disable the auto-generated Main method.
  3. Implement a custom Program.Main using AppInstance.

2 Wire up single-instance behavior in Program.cs

WinUI 3 apps are multi-instanced by default. The Windows App SDK app lifecycle APIs expose AppInstance, which lets you control instancing, redirect activations, and inspect activation arguments. :contentReference[oaicite:3]{index=3}

2.1 Disable the auto-generated Main

The template generates a default Main behind the scenes. To intercept activations as early as possible (before any window exists), you define DISABLE_XAML_GENERATED_MAIN in your project file. The official single-instance how-to uses this exact approach. :contentReference[oaicite:4]{index=4} 

<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>netX.X-windows10.0.19041.0</TargetFramework>
    <UseWinUI>true</UseWinUI>

    <!-- Turn off the generated Main so we can define our own -->
    <DefineConstants>
      $(DefineConstants);DISABLE_XAML_GENERATED_MAIN
    </DefineConstants>
  </PropertyGroup>
</Project>

Replace netX.X with your target (.NET 8–10); the single-instance pattern remains the same.

2.2 Implement Program.Main with AppInstance

The official pattern is: initialize COM wrappers, decide whether to redirect this activation to an existing instance, and only start the WinUI application if you are the primary instance. A DispatcherQueueSynchronizationContext is set up so async continuations can safely run on the UI thread. :contentReference[oaicite:5]{index=5} 

using System;
using System.Diagnostics;
using System.Runtime.InteropServices;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.UI.Dispatching;
using Microsoft.UI.Xaml;
using Microsoft.Windows.AppLifecycle;
using Windows.ApplicationModel.Activation;

public class Program
{
    [STAThread]
    public static int Main(string[] args)
    {
        // Required for WinRT interop in desktop apps
        WinRT.ComWrappersSupport.InitializeComWrappers();

        bool isRedirect = DecideRedirection();

        if (!isRedirect)
        {
            Application.Start(_ =>
            {
                // Wire WinUI to the DispatcherQueue so async/await works as expected on the UI thread.
                var context = new DispatcherQueueSynchronizationContext(
                    DispatcherQueue.GetForCurrentThread());
                SynchronizationContext.SetSynchronizationContext(context);

                _ = new App();
            });
        }

        return 0;
    }

    private static bool DecideRedirection()
    {
        bool isRedirect = false;

        // Activation info for this process (Launch, Protocol, File, etc.)
        AppActivationArguments activationArgs =
            AppInstance.GetCurrent().GetActivatedEventArgs();

        // Your app's unique instancing key
        AppInstance keyInstance =
            AppInstance.FindOrRegisterForKey("SingleInstance.WinUI3.Sample");

        if (keyInstance.IsCurrent)
        {
            // Primary instance: listen for redirected activations.
            keyInstance.Activated += OnActivated;
        }
        else
        {
            // Another instance is already running: redirect this activation to it.
            isRedirect = true;
            RedirectActivationTo(activationArgs, keyInstance);
        }

        return isRedirect;
    }

    // --- P/Invoke helpers to wait for redirection and bring the main window to front ---

    [DllImport("kernel32.dll", CharSet = CharSet.Unicode)]
    private static extern IntPtr CreateEvent(
        IntPtr lpEventAttributes, bool bManualReset,
        bool bInitialState, string lpName);

    [DllImport("kernel32.dll")]
    private static extern bool SetEvent(IntPtr hEvent);

    [DllImport("ole32.dll")]
    private static extern uint CoWaitForMultipleObjects(
        uint dwFlags, uint dwMilliseconds, ulong nHandles,
        IntPtr[] pHandles, out uint dwIndex);

    [DllImport("user32.dll")]
    private static extern bool SetForegroundWindow(IntPtr hWnd);

    private static IntPtr redirectEventHandle = IntPtr.Zero;

    public static void RedirectActivationTo(
        AppActivationArguments args,
        AppInstance keyInstance)
    {
        redirectEventHandle = CreateEvent(IntPtr.Zero, true, false, null);

        // Perform redirection on a worker thread.
        Task.Run(() =>
        {
            keyInstance.RedirectActivationToAsync(args).AsTask().Wait();
            SetEvent(redirectEventHandle);
        });

        const uint CWMO_DEFAULT = 0;
        const uint INFINITE = 0xFFFFFFFF;

        _ = CoWaitForMultipleObjects(
            CWMO_DEFAULT,
            INFINITE,
            1,
            new[] { redirectEventHandle },
            out uint _);

        // After redirection completes, bring the primary window to the front.
        Process process = Process.GetProcessById((int)keyInstance.ProcessId);
        SetForegroundWindow(process.MainWindowHandle);
    }

    // Entry point for redirected activations on the primary instance
    private static void OnActivated(object sender, AppActivationArguments args)
    {
        // Delegate to App so activation handling is centralized.
        if (Application.Current is App app)
        {
            app.HandleActivation(args);
        }
    }
}

The structure above follows the official single-instance how-to, extended to call into a shared App.HandleActivation method that we’ll define next. :contentReference[oaicite:6]{index=6}

3 Centralize all activation logic in App

The Windows App SDK exposes a single AppActivationArguments object that tells you: how your app was activated (launch, file, protocol, startup, …) and any extra payload. You can inspect Kind and Data to parse activation arguments in one place. :contentReference[oaicite:7]{index=7}

3.1 App.xaml.cs: store the main window & handle activations

The idea is:

  • Create and store a reference to your MainWindow on first launch.
  • Call HandleActivation:
    • from OnLaunched for the initial activation, and
    • from Program.OnActivated when redirections arrive.
  • Switch on ExtendedActivationKind (Launch, Protocol, etc.). 
using Microsoft.UI.Xaml;
using Microsoft.Windows.AppLifecycle;
using System.Diagnostics;
using Windows.ApplicationModel.Activation;
using Windows.Foundation;

namespace SingleInstance.WinUI3.Sample;

public partial class App : Application
{
    public static Window? MainWindow { get; private set; }

    public App()
    {
        InitializeComponent();
    }

    protected override void OnLaunched(Microsoft.UI.Xaml.LaunchActivatedEventArgs args)
    {
        // Create and show the main window once.
        if (MainWindow is null)
        {
            MainWindow = new MainWindow();
            MainWindow.Activate();
        }

        // Handle the activation that launched this process.
        var activationArgs = AppInstance.GetCurrent().GetActivatedEventArgs();
        HandleActivation(activationArgs);
    }

    /// <summary>
    /// Central activation handler for launch, protocol, etc.
    /// Called both from OnLaunched and from Program.OnActivated.
    /// </summary>
    public void HandleActivation(AppActivationArguments activationArgs)
    {
        var kind = activationArgs.Kind;

        Debug.WriteLine($"[App] Activation kind: {kind}");

        switch (kind)
        {
            case ExtendedActivationKind.Launch:
                HandleLaunchActivation(activationArgs);
                break;

            case ExtendedActivationKind.Protocol:
                HandleProtocolActivation(activationArgs);
                break;

            // You can add ExtendedActivationKind.File, StartupTask, etc. here as needed.
            default:
                break;
        }
    }

    private void HandleLaunchActivation(AppActivationArguments activationArgs)
    {
        if (activationArgs.Data is ILaunchActivatedEventArgs launchArgs)
        {
            string arguments = launchArgs.Arguments ?? string.Empty;
            Debug.WriteLine($"[App] Launch activation args: '{arguments}'");

            // TODO: route arguments into your navigation / view-model as needed.
        }
    }

    private void HandleProtocolActivation(AppActivationArguments activationArgs)
    {
        if (activationArgs.Data is IProtocolActivatedEventArgs protocolArgs)
        {
            Uri uri = protocolArgs.Uri;
            Debug.WriteLine($"[App] Protocol activation URI: {uri.AbsoluteUri}");

            // Example: parse query string for parameters like ?action=open&id=42
            // and navigate to the appropriate page in your app.
        }
    }
}

The ExtendedActivationKind value and the strongly-typed Data interfaces (such as IProtocolActivatedEventArgs) are part of the rich activation model in Windows App SDK. :contentReference[oaicite:8]{index=8}

4 Register a custom URI protocol for your packaged app

To have your app respond to URIs like myapp://open?foo=bar, you declare a protocol extension in the app package manifest. The “Handle URI activation” article describes the general pattern, which carries over cleanly to WinUI 3 + Windows App SDK. :contentReference[oaicite:9]{index=9}

4.1 Edit Package.appxmanifest (XML view)

  1. Right-click Package.appxmanifest → Open With… → XML (Text) Editor.
  2. Ensure the uap namespace is present on the <Package> element.
  3. Add a protocol extension inside <Applications> … <Application>. 
<Package
  xmlns="http://schemas.microsoft.com/appx/manifest/foundation/windows10"
  xmlns:uap="http://schemas.microsoft.com/appx/manifest/uap/windows10"
  IgnorableNamespaces="uap">

  <Applications>
    <Application Id="App"
                 Executable="$targetnametoken$.exe"
                 EntryPoint="$targetentrypoint$">

      <uap:VisualElements
        DisplayName="SingleInstance WinUI3 Sample"
        Description="Single-instance app with protocol activation"
        BackgroundColor="transparent"
        Square44x44Logo="Assets\Square44x44Logo.png" />

      <Extensions>
        <uap:Extension Category="windows.protocol">
          <uap:Protocol Name="singleinstance">
            <uap:DisplayName>SingleInstance Protocol</uap:DisplayName>
            <uap:Logo>Assets\Square44x44Logo.png</uap:Logo>
          </uap:Protocol>
        </uap:Extension>
      </Extensions>

    </Application>
  </Applications>
</Package>

After deployment, URIs like singleinstance://open?foo=bar will activate your app, and the URI will be available via IProtocolActivatedEventArgs.Uri in your HandleProtocolActivation implementation.

4.2 Quick sanity test

  • Build and Deploy your app (right-click project → Deploy).
  • Press Win+R, type singleinstance://test?source=runbox, hit Enter.
  • Your app should launch (or activate if already running), and the URI should be logged by HandleProtocolActivation.

5 Redirect protocol activations into the running instance

At this point, you have:

  • A custom Program.Main that chooses a primary instance using AppInstance.FindOrRegisterForKey.
  • Redirection of subsequent activations via RedirectActivationToAsync.
  • A centralized activation handler in App.HandleActivation.

When a URI activation occurs while the app is already running, the new process:

  1. Receives AppActivationArguments containing Kind = ExtendedActivationKind.Protocol and the URI payload. :contentReference[oaicite:10]{index=10}
  2. Calls RedirectActivationToAsync targeting the primary instance. :contentReference[oaicite:11]{index=11}
  3. Exits after redirection completes.
  4. The primary instance’s AppInstance.Activated event fires, calling Program.OnActivated, which dispatches to App.HandleActivation.

5.1 Logging and processing protocol args

The HandleProtocolActivation method from earlier already logs the URI. You can expand it to parse parameters and push them into your navigation stack or view-models: 

private void HandleProtocolActivation(AppActivationArguments activationArgs)
{
    if (activationArgs.Data is IProtocolActivatedEventArgs protocolArgs)
    {
        Uri uri = protocolArgs.Uri;
        Debug.WriteLine($"[App] Protocol activation URI: {uri}");

        // Simple example: singleinstance://open/item/123?source=deeplink
        if (uri.Host.Equals("open", StringComparison.OrdinalIgnoreCase))
        {
            string path = uri.AbsolutePath.Trim('/');
            string? query = uri.Query;

            // For example, route to a details page in MainWindow.

    }
}

6 Safely touching UI from redirected activations (DispatcherQueue)

The activation callback attached to AppInstance.Activated is not guaranteed to run on the UI thread. The official single-instance sample uses DispatcherQueueSynchronizationContext so async continuations can hop back to the UI thread, but you still shouldn’t directly manipulate UI from the static Program.OnActivated handler. :contentReference[oaicite:12]{index=12}

6.1 Use the main window’s DispatcherQueue to hop to UI

One safe pattern is to:

  • Keep all UI-facing work in App / window code.
  • From Program.OnActivated, enqueue a call onto the main window’s dispatcher. 
// Program.cs
private static void OnActivated(object sender, AppActivationArguments args)
{
    if (Application.Current is not App app || App.MainWindow is null)
        return;

    // Jump to the UI thread owned by the main window.
    App.MainWindow.DispatcherQueue.TryEnqueue(() =>
    {
        app.HandleActivation(args);
    });
}

This pattern meshes with the DispatcherQueue-based synchronization context recommended in the single-instance tutorial while keeping UI work inside the main window’s thread. :contentReference[oaicite:13]{index=13}

7 Background tasks & advanced scenarios (optional)

Background tasks are orthogonal to single-instancing, but the same activation pipeline concept applies: the Windows App SDK exposes activation kinds and payloads that you can inspect in one central place. :contentReference[oaicite:14]{index=14}

7.1 Where background tasks fit

  • Use background tasks for work that should run when your full UI isn’t needed: timers, push notifications, maintenance, etc.
  • Register them in the manifest or dynamically (depending on trigger type).
  • Within the background task entry point, you can use similar activation reasoning to decide what to do.

The Windows App SDK background tasks docs and the app lifecycle samples show how to wire this up in detail; the instancing and rich activation APIs you’re already using plug directly into that model. :contentReference[oaicite:15]{index=15}

7.2 Unpackaged apps & custom instancing

For unpackaged desktop apps that adopt the Windows App SDK, you can:

  • Use ActivationRegistrationManager to register for protocol/file/startup activation. :contentReference[oaicite:16]{index=16}
  • Combine AppInstance with a custom IPC mechanism (for example, named pipes) to forward arbitrary launch arguments, a pattern explored in community blog posts. :contentReference[oaicite:17]{index=17}

The core idea is still the same: there is exactly one “main” instance that owns UI and activation processing, with other processes doing minimal work and then redirecting/forwarding data.

8 End-to-end checklist

  1. Create a Blank App, Packaged (WinUI 3 in Desktop) project with Windows App SDK 1.8. :contentReference[oaicite:18]{index=18}
  2. Add DISABLE_XAML_GENERATED_MAIN to the project file.
  3. Create Program.cs:
    • Initialize COM wrappers.
    • Call AppInstance.GetCurrent().GetActivatedEventArgs().
    • Use AppInstance.FindOrRegisterForKey with a unique key.
    • Redirect when IsCurrent is false via RedirectActivationToAsync.
    • Attach AppInstance.Activated for the primary instance.
  4. In App.xaml.cs:
    • Store the main window in a static property.
    • Call HandleActivation from OnLaunched.
    • Switch on ExtendedActivationKind and handle launch + protocol.
  5. From Program.OnActivated, marshal to the main window’s DispatcherQueue and call App.HandleActivation.
  6. Edit Package.appxmanifest:
    • Add a windows.protocol extension with your scheme name (for example, singleinstance).
  7. Deploy the app and test:
    • Normal launch from Start menu.
    • Multiple launches (should always focus the same instance).
    • Launching URIs both when the app is closed and when it’s already running.
  8. Optionally, layer in background tasks or additional activation kinds (file, startup, etc.) using the same centralized handler and instance model.
